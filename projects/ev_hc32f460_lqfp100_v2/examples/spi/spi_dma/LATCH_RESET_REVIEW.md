# 频繁擦拭/间歇缺墨：驱动软件复核和第一阶段修正

结论：HC32喷头驱动存在可复现的状态清理缺口及加热时序被中断拉长的风险，
应先修正，不能继续把“函数返回”当作正确驱动。但不能仅凭症状认定为物理堵塞，
也不能证明这些软件问题就是需要频繁擦拭的唯一原因。

依据：用户 M0333N V1.2 规格书第9、11、23页；hc32 source/tph_m0333n.c。
S1..S4低电平采样/高电平锁存，CE为高有效加热门控；采样低脉宽最小0.38us，
典型tFire=2us，最大2.2us。规格书要求最后地址之后紧跟停止时序，循环间留回填时间。

## 确认的问题

1. 原生产函数每个地址切换前直接重新拉高CE，却未先清除四组内部锁存的数据。
   改变D引脚不等于改变已经锁存的值；上一地址的非零数据可能在新地址开门时仍有效，
   直到相应S再次更新。这与多色/不同分区同时使用时不稳定的现象相容，但不是根因证明。
2. 原列结束只把D清零、调用FAST_SET_ADDRESS(0)、拉低CE；没有重新采样四组零数据。
   且FAST_SET_ADDRESS(0)代表地址表第一个有效地址Add1，不是A1..A7全零。
3. 原CE有效段允许中断。若被打断，原有NOP序列无法限制实际加热门控时长。
4. 原函数逐地址开关CE，而规格书典型图是跨地址的连续CE/S循环流水。
   S1..S4相对于CE下降的剩余时间不同，不能用“CE总高电平约2.1us”证明各分区tFire均为2us。
   原NOP函数名/注释也有不一致：delay_40ns只有5个NOP，200MHz理想下仅25ns；
   总时间还包括GPIO总线、Flash、指令和编译选项，不能凭NOP个数认证实物时序。

## 本分支的受控修改（不增加加热参数）

分支 codex/printer-latch-reset，从现有ROW_AUDIT统计版继续：

- CE保持低时，D=0并依次对S1..S4执行零数据锁存；列开始、每个地址完成后、列结束均清理。
- 真实清零地址引脚，不再用LUT索引0冒充全零地址。
- 只在原CE有效窗口内临时屏蔽可屏蔽中断，CE拉低并完成写入屏障后恢复原PRIMASK。
  不在整列、SPI握手或马达行程中长时间关中断。
- VL建立后、VP使能前清理状态；关闭VP前先关CE并清理。
- 维持原有CE内NOP参数、VP/VL使能逻辑、BK数据/运动及HC32分段统计。
  不加预喷、重复发火、提高电压或加长脉宽，也不声称可以用软件清洗堵塞。

清理发生在CE低的门控状态，不是直接把厂家连续CE的典型停止图完全实现了一遍。
完整流水时序及真实0.38us/2.2us限制仍需实测；这版不是“规格书全符合”认证。
若后续修正实际发热周期，必须单独验证，不应靠任意增加延时提高颜色浓度。
未使用的旧fix/standalone实验函数不属于本分支验证的生产调用路径，不要另行调用强制颜色实验。

## 更新和本地验证

BK7258不改，保留当前测试图及参数，不同时调整位置/颜色组合。
HC32仓库根目录执行：

```powershell
git stash push -m "before-latch-reset"
git fetch origin
git switch codex/printer-latch-reset
git pull --ff-only
git log -1 --oneline
```

不要stash pop。打开原MDK/spi_dma.uvprojx，Rebuild后烧录本次固件。
开机应有 `PCTLv1 ROW_AUDIT_v1 LATCH_RESET_v1 ready power=OFF`。
先核实喷头端实际供电符合规格书：VP工作范围12..16V、VL12..15V；
先前示波器若确实在VP测到17.368V，需要解决供电问题，不能用脉宽或清理代码补偿过压。

清洁一次、放好纸、恢复字车起点、两端断电重启，做一次与此前相同的测试。
反馈墨迹照片、是否仍需要擦拭、完整BK/HC日志。不要用反复干打或增加能量代替定位。
如果仍缺墨，保留此版数据与样张，核对D2/S2/CE实际关系和喷头端供电；
必要时查供墨/表面积墨/喷头状态，不能仅凭本次软件改动判定已排除硬件和耗材问题。
